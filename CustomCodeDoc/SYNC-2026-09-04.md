## 6. The dependency-install detour — read this before blaming a merge

`pnpm install --frozen-lockfile` **fails on this repo**, and it is not the
merge's fault. The full diagnosis, because it cost real time:

```
ERR_PNPM_LOCKFILE_CONFIG_MISMATCH  the current "patchedDependencies"
configuration doesn't match the value found in the lockfile
```

### 6.1 It is not the merge — proven with a pristine worktree

```bash
git worktree add --detach /tmp/upstream-pristine af3023f1e
cd /tmp/upstream-pristine && corepack pnpm install --frozen-lockfile
# -> exits 1 with the identical error
```

**A clean checkout of upstream's own tip fails the same way.** Whatever this is,
the fork did not cause it and cannot fix it.

### 6.2 The cause: a host-dependent patch hash

`patches/` is byte-identical to upstream, and the fork's *pre-merge* lockfile
recorded the *same* hash upstream records
(`grbydorkxatbzksnwwfuawwtim` for `@agentclientprotocol/codex-acp@1.6.2`).
Running `pnpm install` on this host recomputes it as
`jb7mkuk6elgpjomlxcdukdpiyy` from unchanged patch content. So the hash is a
function of the pnpm build, not of the repo. `packageManager` pins `pnpm@9.15.4`;
pnpm 10.15.0 was tried and fails identically.

**Consequence: use plain `pnpm install`, never `--frozen-lockfile`, on this host**
— which is what `AGENTS.md` §4 already says. It exits 0 in ~40 s.

### 6.3 Do not commit the lockfile churn

`pnpm install` rewrites 9 lines: the patch hash above (3 sites) and a
`cpu: [arm64, x64]` line under `opencode-ai@1.18.17` that pnpm 9 drops. Both flip
back on a host with the other pnpm, so committing them is pure churn. **The
lockfile staged in this merge is upstream's, byte for byte.** After any
`pnpm install`, restore it before committing:

```bash
git checkout -- pnpm-lock.yaml     # node_modules is unaffected
```

### 6.4 One genuine merge artifact was found here, and fixed

The textual auto-merge of `pnpm-lock.yaml` **kept the fork's stale side** and
dropped upstream's new `cpu: [arm64, x64]` line under `opencode-ai@1.18.17`.
Since the fork adds **no** dependencies — `git diff af3023f1e -- '*package.json'
pnpm-workspace.yaml patches/` is empty — the correct lockfile is upstream's
verbatim, and that is what was staged:

```bash
git checkout af3023f1e -- pnpm-lock.yaml && git add pnpm-lock.yaml
```

**Generalise this.** A three-way textual merge of a lockfile is not trustworthy.
Whenever the fork carries no dependency changes, take upstream's lockfile whole
rather than accepting the merged one.

### 7.5.4 Cap the V8 heap *below* available memory — the counter-intuitive fix

**Worth promoting into §7.1.** `issue-thread-interaction-routes` was being
OOM-killed by the kernel, not failing on logic:

| V8 heap setting | Result |
| --- | --- |
| default heuristic | worker OOM-killed at **18 of 77** after 111 s |
| `--max-old-space-size=2048` | **77 of 77 executed** in 43 s (76 pass / 1 timeout) |

The mechanism: V8 sizes its heap against the **15 GB the host advertises**, grows
toward it, and — with **no swap on this box** (§10) — hits physical exhaustion and
is killed. A ceiling *below* available memory makes V8 collect instead of grow.
Lowering the limit makes the suite finish faster, which reads backwards until you
see that the time was being spent growing a heap toward a wall.

## 10. Host finding — swap is impossible in this container, permanently

Recorded because it will otherwise be re-attempted every session.

An 8 GiB `/swapfile` was created, and `sudo swapon /swapfile` fails:

```
swapon: /swapfile: swapon failed: Operation not permitted
```

**This cannot be fixed from inside the container.** `swapon(2)` requires
`CAP_SYS_ADMIN`, which is absent from the container's *bounding set*
(`CapBnd: 00000000a80425fb`) — the hard ceiling on what any process here can ever
hold. sudo grants uid 0 but cannot add a capability the bounding set excludes.
Swap is also not namespaced: were it to succeed it would add swap to the **host**
kernel, shared with every other container, which is why Docker blocks it.

`/swapfile` is therefore 8 GiB of unusable disk and can be deleted.

What the memory situation actually is:

| | |
| --- | --- |
| `memory.max` | `max` — **no cgroup memory limit** |
| `memory.swap.max` | `max` (moot: `/proc/swaps` is empty host-wide) |
| `memory.current` | ~2.9 GB at rest |
| `memory.events oom_kill` | **3** |

So the container is not capped — it can use the host's full 15 GB. The OOM kills
were V8 growing into physical exhaustion with no swap to absorb the spike, which
is exactly what §7.5.4's heap cap addresses. **The heap cap is the working lever
on this host; swap is not available and should not be pursued again.**
